About Me

I'm Duy Nguyen, an MS Data Science student at Seattle University (GPA 4.0 — College of Science and Engineering Dean's Graduate Student Honor Roll, Winter 2026). My focus is building data systems that researchers can actually use: pipelines that are auditable, databases that reproduce the original analysis exactly, and infrastructure that outlasts the person who built it.

At Seattle University, I have held two research positions. With Dr. Brian Fischer (Mathematics), through summer 2026, I designed a 7-table normalized MySQL database for barn owl auditory neuroscience by ingesting data from two researchers across 110 neurons, 8 owls, and ~261 experiments stored as 14,000+ files in six proprietary formats with no consistent structure. I identified 8 data quality problems, built a 6-phase ETL pipeline to resolve them, and implemented 4 separate loaders to handle the completely different internal .mat file formats each researcher used. The fitting methods alone cover two-sided asymmetric Gaussians, rate-level sigmoids with 5 physiological parameters, Akima spline interpolation, and SVD for response separability. The end result: a 40-line analysis loop that previously required 228 file loads now runs as a single SQL query. With Dr. Wenjing Yang, I work on a quieter problem in medical AI: most vision RAG pipelines for clinical imaging never measure whether the retrieval step actually works. Holding three vision–language decoders frozen and varying only the retrieval encoder across four pretraining substrates, we found that the same contrastive fine-tuning recipe transfers only when the encoder was pretrained in-domain — the others sharpen their training-set separation while held-out retrieval stays tied with a majority-class baseline that ignores the query entirely. That result is a first-author paper now under review at the Pacific Symposium on Biocomputing (PSB) 2027.

Reporting turned out to be the hardest part. Months of work have to become one argument a stranger can follow in twelve pages, and almost all of that happens in revision — cutting results I was attached to, rewriting the same paragraph until my advisor could read it once and know what it showed, and finding the claims that were true but not quite supported. I found it more stressful than any of the modeling, and more useful to have learned.

Working on a five-person data cleaning team for the same neuroscience project, I treat AI tools as a coordination problem, not a coding problem. When teammates ran three different (and silently divergent) versions of a shared renaming script across 36 raw data folders, the bottleneck shifted from writing code to verifying it across people — so I built the layer that catches that: an audit script that traces every violation back to the line of code that produced it, and a deterministic plan → manifest → apply pipeline that replaced the ad-hoc scripts with one reproducible path.

I used Claude Code as a delegation layer. The audit script walks any teammate's OneDrive upload, checks every file against the supervisor's eight stated requirements, and traces each violation back to the exact line in the source notebook that produced it. On one batch it surfaced 164 systematic violations across 16 folders — leftover .gen files, wrong canonical extensions, preserved trial files that should have been deleted — with file lists, teammate attribution, and code-level root causes the team could act on immediately. The replacement pipeline (plan_renames.py → manifest → apply_renames.py) produces uniform output across all 35 viable dates with zero violations.

That pattern — never mutate the raw data, emit a manifest, review it, then apply — is now how the team works. Extending it to a second, undocumented corpus of 870 electrophysiology files left by a former lab member meant every file's fate had to be argued for before anything moved: 226 staged, 26 archived in place, 561 dropped as provably redundant, 57 held for my supervisor, reconciling to all 870. Demanding proof instead of a blanket rule is not ceremony — one file that every heuristic called a redundant duplicate turned out to be the only surviving copy of its recording, and was kept because the evidence never cleared the bar. The same discipline caught an error the project had been carrying in inherited code: its rule for reading experiment type out of a binary header recognised only one of the two ways a parameter sweep could be written, so it mislabeled 22 of 48 files — 12 of them into a plausible-looking but wrong type, with an entire stimulus axis silently deleted. Deriving the type from the recorded trials instead took agreement with ground truth from 29/48 to 48/48.

The part I would defend hardest is that the verification layer points at me too. I run adversarial audits on my own output — independent agents on fenced, non-overlapping questions, each finding then attacked by a second agent whose only job is to refute it. On that corpus the harness caught a blocking bug in code I had just written (154 of 226 rows describing a 21-point measurement as zero points), caught me making the exact mistake I had been flagging in my teammates' work — judging a file by its filename instead of its contents — and made me retract a claim about the data I had already put in writing to my advisor.

My philosophy is that using AI tools isn't the risk — the harder problem is managing a system where everyone uses them and small inconsistencies compound silently across the team's output. I lean on AI heavily for my own throughput, but I spend the saved time on the parts that don't scale: writing the verification layer, tracing root causes back to specific lines of code, framing findings so teammates can self-correct without friction, and making sure the supervisor sees one coherent story instead of seven contradicting drafts. In the AI era, the hardest part of teamwork isn't producing more output — it's making sure the group's combined output is actually correct, reproducible, and aligned with the goal. That standard is worth little if it only ever points outward.

I'm looking for Summer 2027 industry research and data science internships — student researcher, research engineer, or data scientist roles — where the work has clear stakes and the feedback is real.

  1. August 2026

    Submitted Separation Without Transfer: The Retrieval Encoder's Substrate, Not the VLM Decoder, Decides Whether Contrastive Fine-Tuning Transfers in Mammography Report Generation to the Pacific Symposium on Biocomputing (PSB) 2027, with Dr. Wenjing Yang as co-author. The paper is under review.

    PSB 2027 · under review
  2. July 2026

    Found the geometric signature behind the encoder effect: the same fine-tuning recipe collapses the held-out effective rank of the three out-of-domain encoders' embeddings (10.5 to 1.1, 9.1 to 2.4, 20.2 to 2.5) while expanding the mammography-native encoder's from 7.2 to 13.3. Collapse versus expansion separates the encoders whose training-set class separation carries over to held-out data from those where it does not.

  3. July 2026

    Tested whether the effect was specific to the label the encoder was fine-tuned on by scoring the untrained, finer five-class BI-RADS category instead of the three-class suspicion label. The gain held on both retrieval-sensitive decoders (accuracy +23.2% and +14.6%; quadratic weighted kappa 0.100 to 0.302), though nearly all of it landed on the majority BI-RADS categories rather than the clinically decisive ones.

  4. July 2026

    Added a fourth encoder, BioCLIP (organism / tree-of-life images), which shares the other out-of-domain encoders' architecture and fine-tuning schedule but not their pretraining domain. That completed the design: four retrieval-encoder substrates, each evaluated frozen and fine-tuned, crossed with three frozen VLM decoders — 24 evaluation cells. Began drafting the paper in the PSB conference format.

  5. July 2026

    Confirmed the headline result. Fine-tuning the mammography-native encoder (Mammo-CLIP) produced the only arm to clear the held-out majority-class retrieval floor of P@1 = 0.487, moving from 0.513 frozen to 0.585 fine-tuned; the same recipe applied to the generic web-image and biomedical-figure encoders inflated training-set separation but left held-out retrieval tied with that floor. The retrieval gain propagated into the generated reports on the two retrieval-sensitive decoders (suspicion accuracy +20.7% and +15.6% relative to the frozen baseline), while MedGemma did not respond to it. Wrote up the full analysis in a 37-page technical report for my advisor, Dr. Wenjing Yang.

  6. May 2026

    Fine-tuned the retrieval encoder for the first time and found a warning sign: its training-set class separation grew far more than its held-out separation. That overfitting signal is what motivated testing the same fine-tuning recipe on encoders pretrained on different image domains.

  7. April 2026

    On a second research position, with Dr. Brian Fischer, designed a 7-table normalized MySQL schema (owl, recording session, neuron, experiment, tuning parameters, spike reliability, ILD conditions tested) for his lab's barn owl auditory-neuroscience recordings — roughly 14,000 raw files in six proprietary formats, 110 neurons across 8 owls, about 261 experiments — and built the 6-phase ETL pipeline that loads it. An analysis loop that previously required 228 individual file loads now runs as a single SQL query.

  8. March 2026

    Began a critical replication of a published retrieval-augmented mammography report-generation pipeline: explored the CBIS-DDSM dataset first, then switched to VinDr-Mammo (5,000 studies) to match the paper's own dataset, and set up evaluation of three vision-language model decoders (MedGemma, Qwen2.5-VL, LLaVA-Med) across several prompting conditions using the paper's own frozen retrieval encoder.
